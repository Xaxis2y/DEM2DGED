Changes in v0.57.0:
- IMPROVED (mountain-terrain accuracy) "-resample optimize" (dem2dged_compare.
  pick_best_resampling()) always benchmarked its candidate resamplers with a
  hold-out test fixed at 2x decimation, regardless of the ratio the
  conversion actually requested. Which resampler reconstructs terrain most
  accurately is ratio-dependent: a controlled measurement against known
  ground truth (synthetic terrain with realistic mountain slope statistics,
  exact elevation known at every DGED post) found the fixed 2x test reliably
  favours Cubic, but at the 8x-16x ratios steep terrain is often actually
  delivered at, Nearest Neighbor reconstructed up to 3x more accurately (on
  a comparatively low-noise source; Cubic/Average remain the safer pick
  above roughly 1 m of source vertical noise -- "optimize" is an empirical
  measurement against the actual source, so it adapts to this by itself once
  it is testing the right ratio). "optimize" now runs its hold-out test at
  (approximately) the real requested decimation ratio via the new
  pick_holdout_factor(), and "average" -- previously never scored even
  though it is -resample auto's own downsampling default -- was added as a
  fifth candidate. See dem2dged_v0.56.0_mountain_terrain_review.md for the
  full measurement.
- CORRECTED (documentation) the v0.49 Gaussian anti-alias pre-filter
  (-prefilter gaussian) was documented as an accuracy improvement for
  high-relief/mountainous downsampling. The same measurement above found the
  opposite: turning it on increased point-wise vertical error at every ratio
  and every resampler tested (Average/Bilinear/Cubic), by 44-102%, growing
  worse at higher ratios -- because those resamplers already blend multiple
  source samples (a low-pass operation), and stacking a second, independent
  Gaussian low-pass in front of that over-smooths the terrain more than it
  removes aliasing. The feature is unchanged and still opt-in (it may still
  reduce visual banding/moire in an overview -- not measured either way),
  but the CLI help text, GUI dropdown label, and library docstrings no
  longer claim it improves point accuracy on mountainous sources.
- REMOVED -resample rms. gdalwarp's "rms" resampler computes the quadratic
  mean (sqrt(mean(x^2))) of each output pixel's contributing footprint,
  which is mathematically guaranteed to be >= |true mean| for any footprint
  with variation -- never an unbiased estimate of elevation. MEASURED: a 4x4
  footprint with true mean -50.0 m produced +100.0 m under "rms" (150 m off,
  wrong sign), with gdalwarp reporting success and no diagnostic. This is
  documented, standard GDAL behaviour (intended for magnitude quantities
  like backscatter, not signed physical elevation), not a dem2dged bug --
  but nothing warned a user who tried it, and -resample optimize actively
  encourages experimenting with resamplers. -resample rms now fails fast
  with a specific explanation instead of silently corrupting output;
  -resample average is the suggested replacement (the true footprint mean).

Changes in v0.56.0:
- FIXED (A1) try_direct_copy_tile() indexed the source half a pixel off. GDAL
  reports the pixel-CORNER geotransform for an AREA_OR_POINT=Point raster, but
  the code compared that corner against a DGED POST. A correctly registered
  source was therefore always rejected (the fast path was unreachable), and a
  source whose corners happened to land on the post grid was accepted and
  written with every value half a post out of place.
- FIXED (A2) sidecar XML values were never escaped. A source file named
  "DEM_A&B.tif" was enough, with no unusual flags, to make every sidecar in a
  delivery malformed. _xml_escape() is now applied at the write boundary.
- FIXED (A3) the four XML writers used the platform code page while declaring
  encoding="UTF-8". On cp1252 a non-ASCII lineage aborted the conversion
  mid-run with UnicodeEncodeError. All four now write UTF-8, and the validator
  reports a mis-encoded sidecar as a finding instead of crashing on it.
- FIXED (A4) dem2dged_validate.py called sys.exit() at module scope.
  SystemExit is a BaseException, so it passed straight through the
  "except Exception" guards in dem2dged.py and dem2dged_gui.py that exist to
  degrade gracefully. Both guards now raise ImportError.
- FIXED (A5) the Svalbard UTM auto-detect split on the wrong longitudes
  (-6/6/18 instead of 0/9/21/33), resolving 7 of 9 test longitudes to the
  wrong zone. The Norway branch was byte-identical to the generic branch and
  applied no special handling; both warnings went through dl.dp() and were
  invisible without -verbose.
- FIXED (A6) a NaN NoData sentinel defeated both validity masks: a good tile
  reported (0, 0, 100.0), and the pre-filter spread one NaN post into 81. One
  shared valid_data_mask() predicate now serves compute_tile_stats(),
  clamp_tile_to_range() and build_prefiltered_source().
- FIXED (A7) extent reprojection sampled only the four corners, so the curved
  edges of a reprojected rectangle fell outside the box. Measured at 4116 m of
  lost coverage on a 6x5 degree extent at 55-60N -- 0.82 of a level-6 tile,
  and those tiles were never generated. Both bbox transforms now densify each
  edge with 21 points, matching GDAL's own SuggestedWarpOutput.
- FIXED (B1) the GUI is a second converter implementation and had fallen
  behind: no anti-alias pre-filter (the v0.49 headline feature), no per-tile
  failure tolerance (one bad tile aborted the whole file, leaving no table of
  contents or collection metadata) and no "no tiles produced" error. All three
  closed, and a GUI-versus-CLI equivalence test now guards against future
  drift.
- FIXED (B2) inspect_source() read the entire raster into memory and cast it
  to float64 -- 4x an Int16 source -- to obtain a min and a max, and ran twice
  per CLI conversion. It now uses GDAL's streamed ComputeRasterMinMax and
  caches per (path, mtime, size).
- FIXED (B3) a compliance profile absent from the policy file silently meant
  "no thresholds", and an all-INFO result reported overall PASS. Missing
  profiles now fall back to the bundled defaults, and a run that evaluated
  nothing reports NOT_EVALUATED.
- FIXED (B4) direct-copied tiles were written without the data-type-aware LZW
  predictor, so a delivery could mix two compression profiles.
- FIXED (B5) the resume check keyed only on the sidecar, so a deleted or
  corrupted tile beside a surviving .xml read as "already done" and could
  never be regenerated.
- FIXED (B6) the product extent was widened at the top of the tile loop,
  before the skip and failure branches, so tiles that never reached the
  delivery still shaped the collection bounding box.
- FIXED (C3) the validator leaked a file handle reading each sidecar.
- FIXED (C4) unused imports and placeholder-free f-strings removed.

Changes in v0.49:
- NEW OPT-IN GAUSSIAN ANTI-ALIAS PRE-FILTER for high-relief source data:
  -prefilter none|gaussian and -prefilter_sigma (CLI: --prefilter /
  --prefilter-sigma). The default is "none", which reproduces v0.48 output
  BIT FOR BIT -- an existing delivery does not need regenerating, and a
  command line that worked before v0.49 behaves identically after it.
- THE PROBLEM IT ADDRESSES. Downsampling a DEM to a coarser DGED level is
  decimation. Terrain detail with a wavelength shorter than twice the
  TARGET post spacing -- the target's Nyquist limit -- cannot be
  represented at that spacing by Bilinear, by Cubic, by Nearest Neighbor,
  or by any resampler that will ever exist. The part that matters is that
  unrepresentable detail does not quietly vanish: it FOLDS BACK into the
  product at a longer wavelength the grid can represent. The result looks
  like terrain -- plausible ridges and hollows -- in places the real ground
  has nothing of the sort, and because it lands inside the representable
  band, no later choice of resampler removes it.
  Real topography follows roughly a 1/f^beta power spectrum, and rough
  terrain carries proportionally far more short-wavelength energy (ridge
  crests, gully walls, scree, cliff edges) than flat terrain. More
  sub-Nyquist energy going in means more folding back, which is a large
  part of WHY a fixed level degrades faster on high relief. This is a
  DISTINCT mechanism from the interpolation error documented in v0.48, and
  neither of v0.48's two levers (matching the level, -resample optimize)
  touches it.
- MEASURED, NOT ASSUMED (new selftest_prefilter.py). On 1/f^beta fractal
  surfaces -- the spectrum real topography actually follows -- decimating
  2 m posts to 20 m posts and scoring against an IDEAL band-limited
  reference (the best any 20 m product could possibly contain):
      very rough   (beta 1.5)   51.54 m -> 9.27 m   -82.0%
      mountainous  (beta 2.0)   35.74 m -> 9.38 m   -73.8%
      hilly        (beta 2.5)   19.52 m -> 7.14 m   -63.4%
      rolling      (beta 3.0)    8.81 m -> 4.31 m   -51.0%
      smooth       (beta 4.0)    1.38 m -> 1.15 m   -16.4%
      near-planar  (beta 5.0)    0.18 m -> 0.32 m   +72.9%  WORSE
  The last row is the whole reason this is opt-in rather than automatic:
  where there is no short-wavelength energy there is nothing to alias, so
  all a low-pass filter can do is blur real signal. It is also a
  bias/variance trade even where it helps -- it systematically clips real
  summits and fills real valleys. Convert both ways and compare the two
  validation reports on YOUR data before shipping a delivery made with it.
- A METHODOLOGY NOTE WORTH KEEPING. An earlier draft of selftest_prefilter.py
  scored against a two-tone synthetic (one representable sine plus one
  unrepresentable sine) and produced badly misleading numbers -- it made the
  pre-filter look useless at moderate decimation ratios and actively harmful
  at high ones (-191% at ratio 100). The cause was the test surface, not the
  filter: a two-tone surface has almost none of the sub-Nyquist energy real
  terrain carries, so the measurement was dominated by the filter's slight
  attenuation of the one representable tone. Switching to fractal surfaces
  reversed the conclusion completely (+74% to +82% on rough terrain). The
  selftest now documents this so it is not "simplified" back to sine waves.
- NEW IN dem2dged_lib.py: VALID_PREFILTERS, validate_prefilter(),
  gaussian_sigma_for_ratio(), _gaussian_kernel_1d(), _convolve1d(),
  build_prefiltered_source(), cleanup_prefiltered_source().
  * sigma = (ratio - 1) / 2 in SOURCE PIXELS, the standard image-pyramid
    anti-aliasing rule. It is exactly 0 at ratio 1, and 0 for upsampling,
    so the filter is skipped rather than gratuitously blurring; the
    converters print a NOTE saying so instead of silently doing nothing.
  * Pure numpy separable convolution -- deliberately NOT scipy. numpy is
    already required by this project; scipy is not, and adding it to the
    packaged .exe for one 15-line function is a poor trade. Verified
    against scipy.ndimage.gaussian_filter to 3e-13 during development.
  * NODATA IS HANDLED BY NORMALISED CONVOLUTION, not ignored. Filtering a
    raster that stores -32767 in its voids with a plain convolution drags
    that sentinel deep into real terrain along every void margin and
    coastline -- measured at over 13,000 m in testing. Both the data and a
    validity mask are filtered and the result is their ratio, so each
    output is weighted by only the valid neighbours that contributed. Void
    footprints are then restored exactly, to the pixel.
  * Processed in row strips with a radius-sized halo, verified bit-identical
    to a whole-array pass, so multi-gigabyte sources are fine. Output is
    always Float32 (smoothing produces fractional heights; rounding them
    here would quantise twice, since the converter's own -ot still governs
    the delivered tile's type).
- IT IS A SEPARATE PASS OVER THE SOURCE, NOT A gdalwarp FLAG. gdalwarp has
  no low-pass option; its "-r average" comes closest and is what
  "-resample auto" already picks when downsampling, but average is a BOX
  filter with large frequency side lobes and no tunable width. The
  pre-filter writes a smoothed scratch copy to the system temp folder,
  warps every tile from that copy, and deletes it as soon as the last tile
  is written (including on a run that produced no tiles). Tile geometry,
  the -te/-tr grid snapping, post positions, the resampler choice, edge
  reconciliation, the cubic-family range clamp and every metadata field are
  untouched. The clamp range in particular is still taken from the ORIGINAL
  source's true min/max, not the smoothed copy, since it exists to catch
  physically impossible elevations and smoothing narrows the range.
- PROVENANCE. When the filter runs, the sidecar lineage statement records
  it and the sigma used, so a downstream consumer can tell a smoothed
  product from an unsmoothed one from the metadata alone.
- Documentation updated to match: README.md gains an "Anti-alias
  pre-filtering for high-relief sources" section (with the measured table
  above and the caveats), both new flags in the options list, and a
  technical-notes entry; QUICKSTART.html gains both options-table rows and
  an "Aliasing" box under Product levels; new update_manual_v0.49.py adds
  a matching FAQ entry to the Word manual via the existing safe insertion
  mechanism. As with every previous manual script, it has NOT been run
  against the real DEM2DGED_User_Manual.docx (that file is not part of the
  mounted project folder) -- run it locally and review the printed
  [OK]/[SKIP] lines before trusting the result.
- Version bumped to 0.49 across all 12 audit_pure.py-checked declarations.
- NOT RUN IN THE AUTHORING ENVIRONMENT: pytest, audit_pure.py and
  selftest_prefilter.py all need real GDAL, which was not available there.
  The pure-numpy math WAS verified independently (kernel normalisation,
  convolution vs scipy, sigma edge cases, NoData leak behaviour, and
  strip-vs-whole-array equivalence all pass). Run the three GDAL-dependent

Changes in v0.47:
- ACCURACY FIX for "-resample optimize" (dem2dged_compare.py). The hold-out
  cross-validation that ranks Nearest/Bilinear/Cubic/Cubic B-Spline scored
  cubic-family reconstructions RAW and unclamped, while delivered tiles made
  with those same algorithms are clamped into the source's true
  [floor(min), ceil(max)] range before being written
  (dem2dged_lib.clamp_tile_to_range()). A handful of overshoot pixels at
  sharp discontinuities -- pixels no real delivery ever actually contains --
  could therefore inflate RMSE/MAE (squared error weights outliers heavily)
  and make a cubic-family method look far less accurate than what a user
  would actually receive, systematically biasing "optimize" toward Bilinear
  even on terrain where a clamped cubic-family method reconstructs most
  posts more accurately. _holdout_stats() now applies the identical clamp
  before scoring (NoData pixels are left untouched, as
  clamp_tile_to_range() does). Verified with a unit test that this can never
  let a clamped error exceed (ceil(source max) - floor(source min)) -- a
  mathematical guarantee, not a heuristic bound.
- Cubic B-Spline ("cubicspline") added as a fourth measured candidate for
  "-resample optimize" (previously only Nearest/Bilinear/Cubic were
  measured). Safe now that overshoot is clamped -- "optimize" only ever
  picks it when it measures a strictly lower hold-out RMSE than the other
  three candidates on that specific source, so adding it can only improve
  the pick, never worsen it. The manual 3-way GUI "Resampling Comparison
  Test" (COMPARISON_METHODS) is unchanged -- this only affects the
  automatic single-pick "optimize" mode, to avoid disturbing that feature's
  fixed 3-test-folder layout.
- Verified against a deliberately adversarial synthetic terrain (a sharp
  cliff): with the fairness fix in place, "optimize" correctly measured
  Nearest Neighbor as the most accurate reconstruction for that shape
  (Bilinear/Cubic/Cubic B-Spline all blend across a true discontinuity and

  the expected, correct behaviour on genuinely sharp relief -- it is not a

Changes in v0.46:
- VALIDATION TOLERANCE CONFIGURATION. Previous versions (v0.45 and earlier)
  used a fixed 5.0m tolerance for Section H2 (sample-window pixel-level
  comparison between tiles and source DEM). This was based on DGIWG test
  standards using moderate-relief test rasters. However, real-world DEMs like
  SRTM and national datasets have sharp terrain features (ridges, canyons,
  cliffs) where resampling artifacts scale with local slope. Bilinear and
  Cubic interpolation can produce 6-10m errors in sample windows on steep
  terrain, while Nearest Neighbor (piecewise-constant) stays near 0m. The
  v0.45 5m limit was therefore too strict for production conversions.

  v0.46 changes the default to 10.0m (still well below the 32m GSD tolerance
  for level 0 tiles, but practical for steep sources) and ADDS SELECTION:
  * GUI: new radio buttons for "5m (stricter)" or "10m (standard)"
  * CLI: -max-diff 5.0 | -max-diff 10.0 (default now 10.0)
  * Python API: run_validation(max_diff=5.0 | max_diff=10.0) (default 10.0)

Changes in v0.37:

  and dem2dged_gui.py's APP_VERSION fallback, had drifted behind
  dem2dged_lib.py (the single source of truth) during the v0.30/v0.31
  validator-only releases; all four now read 0.32 again
- This packaging script now excludes build/dist output, __pycache__,
  .pytest_cache, and prior release zips from the package instead of
  walking the entire project folder with no exclusions

Changes in v0.31:
- Two more validator false-positive fixes, found auditing a real conversion
  run (report-only; no changes to the converters or to what gets written to
  disk) -- see VALIDATOR_VERSION.txt / dem2dged_lib.py for details

Changes in v0.30:
- Fixed a validator false positive in the file-pairing check (A):
  TABLE_OF_CONTENTS.xml and <product>_COLLECTION.xml are delivery-level
  metadata, not per-tile sidecars, so they were wrongly flagged as
  "missing .tif" on every delivery that included them

Changes in v0.29:
- QUICKSTART.html rewritten for v0.27/v0.28 feature parity: documents
  --org / --abs-hacc / --abs-vacc / --lineage, the GUI Source vertical
  field, level-aware Int16/Float32 data types, the level 0-3 short
  filename form, and automatic in-process validation
- Fixed a stale "v0.15" label and an incorrect GPL-3.0 mention (project is
  GPL-2.0-or-later) in QUICKSTART.html; genericised hardcoded Windows paths
- No functional code changes

Changes in v0.28:
- Fixed a truncated DGED_UTM_TEMPLATE.xml that made every UTM tile's XML
  sidecar invalid (not well-formed) since v0.27
- GUI now calls the same shared conversion logic as the CLI converters
  instead of an independently-maintained copy that had drifted out of spec:
  fixes a half-post pixel misregistration, wrong data type below level 3,
  a stale filename form for levels 0-3, and mostly-blank XML sidecars in
  every GUI-produced tile
- GUI can now perform a real EGM2008 vertical-datum transform (-source-
  vertical), previously accepted by the code but unreachable from the UI
- Validator brought back in sync with the v0.27 converter changes: data-type
  check is level-aware (Int16 for levels 0-2), filename patterns accept the
  current level 0-3 naming, hand-copied fallback tables removed
- dem2dged.py (unified CLI) gained --org / --abs-hacc / --abs-vacc /
  --lineage, previously only reachable via the mode-specific scripts
- Version strings and this packaging script's source path resynchronised
  across the project

Changes in v0.26:
- GUI window-layout fix: the Convert / Stop buttons and progress bar are
  pinned to the bottom of the window (always visible), the rest of the form
  scrolls, and the window opens no larger than the screen work area

Changes in v0.25:
- GUI now shows a completion dialog and reports stopped/error runs instead
  of silently discarding them
- GUI extent reprojection uses all four corners (fixes possible edge-tile
  under-coverage on oblique transforms)
- Packaging scripts now point at the correct source folder

Carried over from v0.24:
- Auto-detect source DEM resolution and auto-suggest a matching product
  level in the GUI, with a warning when the selected level is finer than
  the source (Feature #1)
- Detailed per-tile PASS/WARN/FAIL criteria table in the HTML validation
  report (Feature #2)

Installation:
1. Extract dem2dged_v0.44.zip
2. Run rebuild_exe.bat to compile
3. Execute dem2dged.exe when ready
