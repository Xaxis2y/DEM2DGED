Changes in v0.62.10:
- Fix: the CGVD2013 separate vertical correction failed inside the GUI with
  "Grid ca_nrc_CGG2013i08.tif / us_nga_egm08_25.tif is not available" because
  PROJ's own network access did not deliver grids from the conversion worker
  thread. dem2dged now downloads the two grid files itself (urllib, once) from
  https://cdn.proj.org/ into %LOCALAPPDATA%\dem2dged\proj_grids (override with
  DEM2DGED_GRID_DIR; DEM2DGED_NO_GRID_DOWNLOAD=1 forbids the download) and adds
  that folder to the PROJ search paths. Downloads use a .part file, a size cap
  (600 MB), a check that the file opens as a raster, and an atomic rename; the
  file name must match a strict whitelist. The SHA-256 of each grid is recorded in
  vertical_correction.json. New CLI option: dem2dged_vertical.py --fetch-grids.
- Error text: a missing-grid failure is now summarised as "PROJ cannot find the
  geoid grid file(s) ...", and the full PROJ text kept in vertical_correction.json
  is capped at 4000 characters.
- Wording: the second route used for the node cross-check shares the same geoid
  grid files as the first; it is documented as a check of the horizontal-frame
  handling, not as an independent check of the grids.
- Tests: tests/test_v06210_regressions.py (fake gdal/osr/urlopen for the download
  logic; two opt-in real tests with DEM2DGED_TEST_NETWORK=1).
- Version constants of dem2dged_vertical.py, dem2dged_datum.py and
  dem2dged_reference.py and the TEST_REFERENCE script are bumped to 0.62.10.
Changes in v0.62.9:
- CGVD2013 sources on generic NAD83(CSRS) data (for example the NRCan HRDEM
  tiles in Ontario) are now converted instead of stopping with "Cannot find
  coordinate operations". Measured cause (v0.62.8 diagnostics, PROJ 9.8.1):
  PROJ defines the CGVD2013 grid operations only for NAD83(CSRS)v6 or ITRF2008
  and joins the generic CRS to them with a BALLPARK offset, which the strict
  guard correctly refuses. The one ballpark route PROJ offers (through v6) shifts
  heights by +1.09 m, where five independent routes agree on -0.022 m at the same
  point. The strict guard is NOT loosened.
- New separate vertical correction (dem2dged_vertical.py): the CGVD2013 ->
  EGM2008 height difference is evaluated on a coarse node grid (about 1 km) with
  ITRF2008 as the context CRS, cross-checked at every node through an independent
  NAD83(CSRS) realisation (v8, v7, v4 or v3), refused when the two routes differ
  by more than 0.02 m, interpolated bilinearly and added to a temporary copy of
  the source. The copy has the same grid, CRS and metadata; horizontal
  georeferencing is not changed; NoData stays NoData. The temporary copy is
  deleted after the file is converted.
- Only CGVD2013 (EPSG:6647) uses this route, because it is the only datum whose
  routes have been measured. Any other datum keeps the old behaviour: the strict
  check runs and the conversion stops if it fails.
- The route is recorded: vertical_operation_check.json and
  vertical_correction.json next to the tiles, and "vertical_route" in
  DEM2DGED_Conversion_Manifest.json (declared datum, route, both contexts, the
  largest difference between the two routes, shift range, node grid, and the
  accuracies stored in proj.db: 0.03 m CGVD2013 <-> ITRF2008, 0.113 m
  WGS 84 -> EGM2008; stated accuracies, not measurements).
- Validation, terrain QA and the evidence files still compare the output with
  the ORIGINAL source heights, as for every vertical conversion; the datum
  shift therefore appears as a small bias (about -0.02 m in Ottawa).
- The "Conversion failed" dialog no longer prints two PROJJSON documents: the
  reason is one short sentence; the full PROJ text is kept as "reason_full" in
  vertical_operation_check.json.
- The command line (dem2dged.py) uses the same route. Calling dem2dged_geo.py or
  dem2dged_utm.py directly with -source_vertical 6647 still stops at the strict
  check (use dem2dged.py).
- Diagnostics added: DIAG_PROJ_VERTICAL, DIAG_PROJ_OPS, DIAG_PROJ_DB.
- Command line to try the correction on one file without the GUI:
  python dem2dged_vertical.py my_dem.tif --vertical 6647 [--out corrected.tif]
- Regression tests: tests/test_v0629_regressions.py.

Changes in v0.62.8:
- New "Detect" button next to Advanced > Source vertical. When a conversion is
  held because the source has no vertical reference, Detect looks for the datum
  in the places a person would look and lists each hint with where it came from
  and how reliable it is: the vertical CRS inside the file (high), datum names in
  the GeoTIFF metadata tags (high/medium), datum names in text/XML/JSON/readme
  files next to the DEM (medium/low), and the NRCan HRDEM / USGS 3DEP tile naming
  convention (medium, using the datum declared in reference_catalog.json).
- Nothing is applied silently. The box is pre-filled only when the high/medium
  evidence agrees on ONE datum, and only after you press "Use EPSG:xxxx".
  Conflicting or weak evidence is shown but not applied. PDF documents next to
  the data are not searched. The datum is never inferred from the height values.
- What was detected and what you confirmed is recorded in
  source_metadata.json ("vertical_declaration") next to the tiles.
- The "Conversion held" dialog and the log now point at Detect.
- New module dem2dged_datum.py (also a command line:
  python dem2dged_datum.py my_dem.tif [--json]). It never uses the network and
  never changes the source raster.
- Regression tests: tests/test_v0628_regressions.py.

Changes in v0.62.7:
- Find reference: the search table has a new "Window (M cells)" column and the
  detail pane states the download size, so a window larger than the 40-million
  cell cap is visible BEFORE you press Download clip (v0.62.6 only reported it
  after the download had started, e.g. "window of 174.5 million cells exceeds
  the limit of 40.0 million").
- New "Max cells (millions)" box next to the buttons (default 40). If the
  selected window is larger than the box, the dialog offers to raise it and
  continue; the tool will not go above 1000 million cells.
- The download time limit now scales with the window (120 s + 4 s per million
  cells) instead of a fixed 120 s, so a big healthy download is not killed.
- The download confirmation shows the window size and warns when less than 90%
  of your area holds heights in the chosen dataset.
- Coverage probes now also return the window size (window_cells).
- Regression tests: tests/test_v0627_regressions.py.

Changes in v0.62.6:
- Fixed the "Not responding" freeze in Find reference. Root cause (measured with
  DIAG_FREEZE_v0.62.5.py and DIAG_TK_BISECT_v0.62.5.py on the DGED environment,
  GDAL 3.13.3): after a GDAL /vsicurl/ network read in a Python THREAD, the next
  DLL load in the main thread deadlocks. The Search button ran exactly that in
  a thread of the GUI process, so the GUI froze the next time it needed a DLL
  (tkinter, native folder/message dialogs). It was not the GIL: GDAL released it.
- Search (catalog query and coverage probes) now runs in a separate worker
  process, like the download already did, and the GUI only polls it. The
  worker's progress lines appear live in the log and the status line.
- The Cancel button now cancels either a search or a download.
- dem2dged_reference.py refuses remote GDAL reads from a non-main thread
  (DEM2DGED_ALLOW_THREADED_VSICURL=1 re-enables them for diagnostics only).
- Regression tests: tests/test_v0626_regressions.py.

Changes in v0.62.0:
- New reference finder (dem2dged_reference.py, reference_catalog.json): looks up
  open lidar DEMs that cover your source extent - NRCan HRDEM (Canada, STAC
  API) and USGS 3DEP 1 m / 1/3 arc-second (US, TNM Access API) - and clips ONLY
  your area (no resampling, window capped at 40 million cells) into a small
  GeoTIFF with a *_reference.json sidecar (identifier, SHA-256, declared
  accuracy, vertical datum, license, warnings).
- Coverage check: a dataset's outline can be far larger than the area it has
  heights for (the first live test clipped two tiles that held no data over
  the test box). Search now samples each of the best candidates over your
  area, shows "Data in area", ranks datasets without data last, and the
  automatic choice only takes a dataset with at least 90% valid heights.
- GUI: "Find reference..." button next to the independent-reference Browse
  button. Search lists datasets with a "fit for the selected DGED level"
  column; Download clip fills the reference path and identifier boxes.
- Command line: python dem2dged_reference.py --source dem.tif --level 5 --list
  (or --bbox MINLON MINLAT MAXLON MAXLAT; --pick N to clip).
- Suitability rule of thumb (not a DGIWG rule): OK if the reference's declared
  LE90 <= the level's vertical random 90% limit / 3; MARGINAL if <= limit / 2.
  No open dataset reaches OK for levels 6 and finer; those need surveyed
  ground control points.
- Network use happens only when you press Find reference / run the command.
  Only the bounding box is sent. Declared accuracies are the providers', not
  measured by DEM2DGED, and a download does not prove independence.
- No conversion, tiling, resampling, metadata or compliance logic changed.
- Test: TEST_REFERENCE_V0.62.0.py (offline unit tests + live Ottawa / Washington
  DC clip test, writes logs\reference_test_*.log / .json).

Changes in v0.58.0:
- Added "Show DGED Differences" to DGED_Loader.pyt.

  elevation_diff.tif as the signed DGED-minus-source difference, loads and

Changes in v1.0.0 (initial standalone release):
- DGED_Loader.pyt: ArcGIS Pro Python Toolbox, "Load DGED Tiles" tool.
  Main folder + multiple hand-picked subfolders (both optional, at least
  one required), recursive on/off toggle, optional group-layer
  organisation, optional Build Pyramids pass. Verified against a mock
  arcpy harness (27 checks: parameter defaults/order, multivalue parsing
  via both the iterable-value and valueAsText-fallback code paths,
  recursive vs. non-recursive walking, folder/tile de-duplication,
  missing-.xml-sidecar warnings, group create/add/remove sequencing, the
  no-folders-provided error path) -- real arcpy.mp calls were not
  exercised, since no ArcGIS Pro install is available in the build
  environment; test end to end in Pro before relying on it for a real
  delivery.
- DGED_Load_Tool_script.py: same logic as a flat GetParameterAsText
  script, for building a native .atbx via ArcGIS Pro's Script Tool
  wizard (see ATBX_WIZARD_GUIDE.md). 4 additional parity checks against
  the same mock harness.
- .atbx was deliberately NOT hand-built: it's a zipped, Esri-proprietary
  format with no published schema, and Esri's own guidance is to build
  it inside Pro rather than by hand. DGED_Loader.pyt is the guaranteed-
  working primary deliverable; ATBX_WIZARD_GUIDE.md covers the ~2-minute
  guided path to a genuine .atbx if you specifically need that container.

Installation:
1. Extract the DEM2DGED v0.58.0 release, or `DGED_Loader_v0.58.0.zip`.
2. In ArcGIS Pro, Catalog pane > browse to this folder > double-click
   DGED_Loader.pyt to add it as a toolbox.
3. Open a map, run "Load DGED Tiles" from inside it.

See README.md for the parameter reference and troubleshooting, and
ATBX_WIZARD_GUIDE.md for the native-.atbx path.
